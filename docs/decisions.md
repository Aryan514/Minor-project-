# Design decisions and deviations from CLAUDE.md

Every place where the implementation had to choose something CLAUDE.md leaves open, or deviates from it,
is recorded here with the reason.

| ID | Decision | Reason |
|---|---|---|
| D1 | `asyncua==1.1.8` (not 2.x). | CLAUDE.md §2 says "latest 1.x"; approved by the student at CP0. |
| D2 | Initial control state is `ONLINE_LOCAL` (authority OPERATOR). | Not fixed by CLAUDE.md; approved at CP0. Scenarios switch to REMOTE with the console. |
| D3 | Control-state changes and the lease are also routed through `arbiter.decide` with two extra actions, `SET_CONTROL_STATE` and `SET_LEASE` (allowed for OPERATOR only, in every state). | Rule 5 says every command from any origin goes through the arbiter, including the operator console. CLAUDE.md §4 says control state is "changed by the operator console". Encoding this in the arbiter makes the no-bypass test cover console commands too. The §6.4 table for START/STOP/EC_WRITE is unchanged. |
| D4 | A state change writes separate audit records: `command_ok` (the accepted command), then `state`/`authority`/`ec_write` (the change), then `event` (the CEID). Each has its own seq. The event's DVID 101 `EventSeq` is the seq of the **event** record. `CommandResult.seq` is the seq of the `command_ok`/`*_rejected` record. | Keeps one record per fact, so the audit log can be replayed to reconstruct state (tested in `test_core.py`). The checker joins client data on the event seq. |
| D5 | The harness drives the operator console through a local TCP control socket `127.0.0.1:5100` (one text command per line, one reply line). | CLAUDE.md §9 lets us pick "a small local control socket or command file". A socket gives the harness the command result synchronously; a file would need polling. |
| D6 | `LastEventSeq` (SVID 5) is the seq of the last record of kind `event`, `alarm_set` or `alarm_clear`. It is derived, not separately audited. | Auditing it would create a record for every record. |
| D7 | Unknown RCMD / unknown ECID are rejected **before** the arbiter is consulted (there is no action to decide on). They are still audited as rejections and emit CEID 1005. | Nothing changes, so no bypass is possible. |
| D8 | Rejection codes for operator console commands reuse the HCACK mapping (2 = not allowed / wrong state, 5 = already in requested state). | Gives one uniform `CommandResult` for every command. |
| D9 | `pytest.ini` sets `--basetemp=.pytest_tmp`. | On this Windows machine pytest cannot open the system temp folder (`PermissionError`). Tests are unchanged. |
| D10 | OPC UA `TempHighLimit` is read-only; writes go through the method `SetTempHighLimit(value)`. | CLAUDE.md §8.2 fallback, chosen by the student at CP1 approval; reasons in `library_notes.md` B.6. |
| D11 | One-shot client actions log their reply to `runs/<id>/ua_client_actions.jsonl` / `gem_host_actions.jsonl`, not to the listening client's receive log. | The listener and the one-shot are different processes. Appending to one file from two processes is not atomic on Windows. |
| D12 | The UA dispatcher worker hops into the asyncio loop with `asyncio.run_coroutine_threadsafe(...).result()`. This uses `loop.call_soon_threadsafe` internally. | CLAUDE.md §6.3 asks for `call_soon_threadsafe`. Waiting for the coroutine to finish keeps the UA door strictly in seq order (I2). The waiting happens on the UA worker thread, never on the core. |
| D13 | UA variables carry two names for one GEM state: `ControlState` (String) and `ControlStateId` (Byte = SVID 2), and the same for ProcessingState. Only the numeric ones carry GemId/GemKind/GemFormat. | CLAUDE.md §8.1 tree. The string is for humans and the numeric one is the GEM mapping. |
| D14 | The UA door's initial values come from a core snapshot taken **after** subscribing to the dispatcher. Variable updates with seq ≤ snapshot seq are skipped, but events are still processed (logged as `dropped_no_link` if nobody listens). | Avoids re-applying stale values queued before the snapshot. |
| D15 | `gem_host --listen` opens a local relay port `127.0.0.1:5101`. One-shot `gem_host --start/--stop/--set-limit/--status` send their request through the listener's HSMS session when a listener runs, and open their own session otherwise. | The equipment's passive HSMS side accepts exactly **one** session (secsgem `TcpServerConnection`, `listen(1)` and the listening socket is closed after accept), which is normal for HSMS-SS. Without the relay, a one-shot command could not run while the listener is connected. Every reply records `via: listener | own_session`. |
| D16 | S6F11 `DATAID` = the event's seq. | DATAID is free-form in GEM. Using the seq gives a second copy of the join key that is visible in Wireshark. |
| D17 | S1F15 (host requests OFFLINE) is answered with S1F0 (abort) when refused. | OFLACK has only the value 0 = acknowledge, so a refusal has no code. S1F0 is the standard SECS-II "transaction aborted" reply. The attempt is still audited and CEID 1005 is emitted. |
| D18 | `harness/live_view.py` tails the run's JSONL logs (`gem_host.jsonl`, `core_audit.jsonl`, `ua_client.jsonl`) instead of subscribing to the dispatcher in-process. The core column is seeded with the `config.py` start values, because the audit records only changes. | A separate process cannot join the core's dispatcher, and the equipment allows only one HSMS session. Reading the receive logs shows exactly what each client actually got, which is the point of the view (N3). CLAUDE.md §6.3 lists "live view" as a dispatcher subscriber; this is the deviation. |
| D19 | The GEM listener reads SVIDs 1–5 (S1F3) and ECID 201 (S2F13) once after setting up reports, and logs it as `kind=status`. | GEM is event-driven: without this the host would not know the starting control state or limit until the first event. |
| D20 | The GEM door uses HSMS T3 = 3 s (reply timeout), not the 45 s default, and logs `sent` only if the host answered with the expected reply (S6F12 / S5F2). S6F0/S5F0 or no reply are logged as `error`. | With 45 s, one S6F11 in flight when the host dies would block the single GEM worker for 45 s. If the host came back meanwhile, the queued events would be delivered late, which looks like spooling but is not. A reply other than F12 means the host did not accept the event, so `sent` would hide a loss (I6). |
| D21 | Scenario evaluation window `[t_start, t_end]` = from "both clients listening" to "actions done + 2 s"; conflict rounds are anchored on the core seq read just before the barrier. | See `docs/invariants.md`. Teardown events are excluded, and Windows clock granularity makes time windows ambiguous for rounds. |
| D22 | The runner kills client/equipment processes with a process-tree kill (`taskkill /T /F` on Windows). | `.venv\Scripts\python.exe` is a launcher with a child interpreter. Killing only the launcher could leave the real GEM host alive, holding the single HSMS session. |
| D23 | The GEM host decodes S6F11 for reports it did not define itself by falling back to its fixed scheme (RPTID = CEID, VIDs from `config.py`). | After a host restart the equipment still has the previous session's reports enabled (correct GEM behaviour) and sends them before the new session re-defines them. secsgem's host raised KeyError and replied S6F0, so the event was lost at the client. This only changes our test client, not the equipment. |
| D24 | One run is committed as the sample: `runs/sample_S3` (a real S3 run, a copy of `S3_20261124-004854`, the run reported in `results/S3_summary.md`). | CLAUDE.md §3 allows one sample run. S3 contains conflict rounds, so the self-test can exercise all five corruption cases incl. I5. |
| D25 | `harness/demo.py` reuses the scenario runner (`Run`, `race`, `kill_tree`) and writes its checker report into the demo's own run folder (`runs/DEMO_*/report/`), not into `results/`. On Windows it opens the live view in a new console window (`CREATE_NEW_CONSOLE`); elsewhere it prints the command. | The demo inherits process handling already proven by the scenarios. The demo run is evidence for the panel but not part of the reported results. |
| D26 | Web dashboard `harness/web_view.py` + `web_view.html`: stdlib `ThreadingHTTPServer` + Server-Sent Events, bound to 127.0.0.1, read-only (tails the five JSONL logs). The invariants panel calls `checker.check_run` on the records seen so far. Live runs are judged only up to 2 s before the newest record; a finished run (scenario.json present) is judged on its scenario window, exactly like the checker CLI. | Same data source as `live_view.py` (D18). Reusing the checker and live_view's column logic means the page cannot show numbers different from the checker (`tests/test_web_view.py`). The 2 s edge keeps in-flight events from being shown as "missing". |
| D27 | `harness/demo.py --auto` pauses `--step-delay N` seconds (default 6, 0 = no pause) before each step. Without `--auto` nothing changes (Enter as before). | `--auto` had no pause, so a viewer could not follow the browser dashboard. The pause comes after the step's one-line explanation is printed and before the step runs. |
| D28 | The scenario runner (also used by the demo) waits for the equipment's `READY run_id=…` line instead of probing ports 4840/5000 by connecting. The relay readiness probe only touches port 5101. | A connect-and-close probe on the HSMS port takes the equipment's single HSMS session. With Npcap loopback capture active, the probe's abrupt close left secsgem's passive side refusing every later connection, so the demo's GEM host never connected (found in the first capture attempt). `main.py` prints READY only after both doors have started, so reading it is both passive and exact. No core, arbiter, adapter or checker logic changed. |
| D29 | **Deviation from the dashboard's read-only rule (D26):** in live mode on 127.0.0.1 the dashboard has a control panel (`harness/control_panel.py`). It starts/stops equipment + both listening clients exactly as `harness.demo` does (`scenarios.Run`), and sends commands only through the entry points any external user has: the GEM host's command port 5101 (real S2F41/S2F15 on HSMS), the `clients.ua_client` one-shot process (real OPC UA Call), and the equipment console's control socket. It never calls the core, so every command passes the arbiter exactly as for any client. POST actions need an `X-Panel: 1` header: a cross-origin page cannot send it without a CORS preflight, which this server never approves. The panel is disabled in replay mode, with `--no-control`, and when `--host` is not loopback. The views still only read the run logs. | Lets the panel show live that the system is engineered (real replies, real reasons) without creating a bypass path (rule 5). Panel-driven runs are judged by the checker on Stop (verified PASS). |
| D30 | Wire logs. SECS-II: `equipment/wire_log.py` attaches a JSONL handler to secsgem's own `communication` logger, which already reports every HSMS message with its SML. It is attached in `equipment/main.py` (equipment side, `gem_wire.jsonl`) and `clients/gem_host.py` (host side, `gem_host_wire.jsonl`). OPC UA: `clients/ua_client.py` logs its service calls (sessions, CreateSubscription, CreateMonitoredItems, Call, Browse) and every received notification at client API level, one file per process (`ua_wire_<role>_<pid>.jsonl`, D11). | The user asked for an adapter-side SECS log without adapter logic changes. Hooking the library's existing logger achieves that with zero adapter edits. UA records are labelled "as logged by the UA clients" because they are API-level, not decoded packets (packets: `results/demo_capture.pcapng`). |
| D31 | Panel "Both START at once" is recorded as an I5 conflict round only when it is a real conflict: processing IDLE and the authority holder (`arbiter.authority_holder`) is GEM_HOST or UA_CLIENT. The expected winner is that holder. Other presses (e.g. in LOCAL, where the policy rejects both) are shown but labelled "not counted for I5". | I5 is defined for conflicting commands where one may win. A press in LOCAL would otherwise fail I5 for a reason that is not a defect. |
| D32 | `harness/race_demo.py` contains a deliberately UNSAFE check-then-act variant (check under the lock, release, sleep 1 ms injected on purpose, apply). It lives only in that script, never in `equipment/`. Both variants race OPERATOR vs UA_CLIENT in EQUIPMENT_OFFLINE + lease. | In REMOTE the policy already rejects UA_CLIENT, so even an unsafe core could not produce two winners there. Only when both contenders are allowed does atomicity make the difference (same setup as `tests/test_race.py`). |
| D33 | Optional tshark packet counter in the control panel (`-T fields -e tcp.srcport -e tcp.dstport` on the loopback adapter, ports 5000/4840), started with the panel's system and hidden when tshark is not found. | Passive capture only, no new Python dependency. Shows that real packets flow, as a count. |
| D34 | User guide screenshots (`docs/user_guide/`) were taken by a headless Microsoft Edge driven over the DevTools protocol (stdlib-only script, not committed) that pressed the dashboard's own buttons; the fixed footer is hidden during capture only. Callouts are drawn with Pillow (`docs/user_guide/annotate.py`), the PDF is printed by headless Edge (`build_pdf.py`). Pillow was installed into the venv for this documentation step only and is not added to `requirements.txt`. | The testbed needs no image library; only the guide tooling does. Pressing the real buttons means the screenshots show real replies and a real checker verdict (run `PANEL_20261124-182143`, PASS). |
| D35 | Known dashboard issue left unfixed (task rule: no harness changes): `harness/web_view.html` defines `showResult` twice (Results tab renderer and control-panel reply box). The later one wins, so the Results tab stays on "loading…". Documented in the user guide (A.5, Part C); fix = rename the control-panel function to `showCmdResult` (lines 492–503), awaiting approval. | Found while taking the Results tab screenshot. |
